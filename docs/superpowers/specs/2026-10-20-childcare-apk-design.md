# 가정 내 자본주의 — APK 앱 재설계 (설계 문서)

작성일 2026-10-20 · 상태: **검토 대기** (승인 전에는 구현하지 않는다)

## 1. 목적과 성공 기준

- 아들 용돈·집안일 포인트를 **부모 폰 + 아들 폰**이 함께 쓰는 앱. 웹페이지가 아니라 **APK로 설치**해서 쓴다.
- 성공 기준
  1. 부모가 하는 일(미션 내주기, 승인, 생활비 적용)이 **아들 폰에 5초 안에** 보인다. 앱을 다시 열면 **즉시** 보인다.
  2. 아들이 누른 동작(요청, 앞가림 체크)이 **하나도 버려지지 않고** 서버에 반영되고, 화면은 항상 서버 상태와 같다.
  3. 부모가 어느 날짜를 보고 있든, 시킨 일은 아들 폰에 보인다. 자정이 지나도 안 끝난 일은 남는다.
  4. APK를 PC 설치 없이 GitHub에서 받아 두 폰에 설치할 수 있다. 업데이트 때 지우고 다시 설치하지 않아도 된다.

## 2. 범위 밖 (이번에 하지 않음)

푸시 알림 · iOS · Play 스토어 배포 · 오프라인에서 오래 쓰기(짧은 끊김만 견딤) · 여러 자녀 · 웹 버전 유지(기존 GitHub Pages 사이트는 APK 전환 후 폐기).

## 3. 기존 앱의 문제 진단

| 증상 | 원인 (코드에서 확인) |
|---|---|
| 부모가 시킨 일이 아들 폰에 안 뜸 | 서버가 미션을 **만든 날짜에만** 내려줌(`missions.day = 보고 있는 날짜`). 부모가 어제/다른 날짜를 보며 만들면 아들 "오늘"에 안 나옴. 자정이 지나면 미완료 미션도 사라짐 |
| 체크박스가 말을 안 들음 | ① 요청 처리 중 다른 체크를 누르면 동작이 **조용히 버려짐**(`busy`). ② 체크박스는 브라우저가 먼저 체크 상태로 바꾸는데, 서버 결과가 이전과 같으면 화면을 다시 그리지 않아 **화면≠서버**가 남음 |
| 반영이 느림 | 8초 폴링 + 앱이 돌아올 때 즉시 갱신 안 됨 |

## 4. 접근 방식

**A안 채택: "서버가 항상 정답" + 직렬 액션 큐 + 상태 카드 UI.**
(B 오프라인-우선 동기화는 충돌 처리가 과함, C 기존 화면 패치는 "처음부터"와 다름 → 제외)

## 5. 아키텍처

```
APK (Capacitor 안드로이드 셸, WebView)
 └─ www/ (정적 파일, 빌드 도구 없음, ES 모듈)
      ├─ api.js      Supabase RPC 호출 (fetch, 15초 타임아웃, 오류코드 → 한글)
      ├─ store.js    상태 보관 + 액션 큐 + 폴링/복귀 갱신 (화면과 분리, 단독 테스트 가능)
      ├─ ui.js       토스트, 하단 시트, 확인창, 햅틱 (alert/confirm 미사용)
      ├─ lock.js     부모 화면 PIN 잠금 (기존 기능 이식)
      ├─ child/      오늘 · 내역 · 설정 화면
      ├─ parent/     현황·승인 · 정산 · 관리 · 설정 화면
      └─ app.js      역할 판별(열쇠 → get_state.role), 탭 라우팅, 연결/가족 만들기 화면
Supabase (기존 프로젝트) — 테이블 잠금(RLS), 기기별 열쇠 + SECURITY DEFINER RPC (기존 구조 유지)
```

- 플러그인: `@capacitor/app`(앱 복귀 이벤트·뒤로가기), `@capacitor/share`(연결 코드 공유), `@capacitor/haptics`(촉각 피드백). 그 외는 쓰지 않는다.
- 앱 ID `kr.ynofire.childcare`, 이름 "가정 내 자본주의".
- 열쇠(48자리)는 WebView 로컬 저장소에 보관. 서버에는 해시만 있다(기존과 동일). 복구 코드 = 부모 열쇠(기존과 동일).

## 6. 동기화 엔진 (store.js) — 이번 재설계의 핵심

1. **상태는 서버 응답이 유일한 정답.** 모든 RPC가 전체 상태를 돌려주고, 클라이언트는 그걸로 화면 상태를 통째로 교체한다. 변경 감지로 "다시 그리기 생략" 같은 최적화는 하지 않는다 (불일치의 원인).
2. **액션 큐(FIFO, 직렬).** 사용자가 누른 동작은 전부 큐에 들어가 순서대로 서버에 보낸다. 처리 중에 눌러도 **버리지 않는다**. 같은 카드를 연타하면 마지막 의도만 남도록 합친다(예: 체크 on→off→on → 최종 on 1회).
3. **낙관적 표시는 "요청 중" 상태로만.** 누른 카드는 즉시 "요청 중…"(스피너)으로 바뀌고, 서버 응답이 오면 서버 상태로 확정된다. 체크 표시를 임의로 먼저 켜지 않는다.
4. **실패 처리.** 서버가 거부하면(`duplicate`, `bankrupt` 등) 카드를 서버 상태로 되돌리고 토스트로 이유를 한글로 보여준다. 네트워크 실패는 큐에 남겨 두고 "연결 확인 중" 띠를 보여준 뒤 복구되면 자동 재시도한다. **큐는 기기 로컬 저장소에도 보관**해서, 오프라인 중 앱이 종료돼도 다음 실행 때 이어서 보낸다. 큐 항목은 모두 **의도 기반·멱등**(`toggle_item(on/off)`, 중복 요청은 서버가 `duplicate`로 거절)이라 재시도해도 이중 반영되지 않는다.
5. **갱신 시점.** 앱 실행 직후 · 앱 복귀(`resume`/`visibilitychange`) · 네트워크 복구 · 내가 동작한 직후(큐가 비면) · 화면 켜진 동안 5초마다. 응답에는 요청 순번을 붙여 **오래된 응답은 버린다.**
6. **새 일 표시.** 마지막으로 본 시점 이후 새로 생긴 미션/심부름 승인 결과에는 NEW 배지, 탭 아이콘에 숫자. (마지막 본 시점은 기기 로컬에 저장)

## 7. 화면 구성

공통: 어두운 남색 바탕 + 노란 강조(기존 브랜드 유지), 터치 영역 최소 56px, 하단 탭 바(안전 영역 반영), 큰 숫자 잔고, 모든 팝업은 앱 안 시트/토스트. 상세 시각 디자인은 구현 단계에서 frontend-design 지침으로 다듬는다.

### 7.1 아들용 (탭 3개)
- **오늘**
  - 상단: 잔고 + 상태(정상/마이너스 차단/파산).
  - **시킨 일(미션)**: 날짜와 무관하게 완료될 때까지 맨 위에 남는다. 카드 상태 = `새 일 → 요청 중 → 승인 대기 → 완료` / 거절 시 `거절됨 → 다시 하기`.
  - **앞가림**(하면 +): 상태 카드. 파산이면 잠금 표시.
  - **심부름**(요청 후 승인): 상태 카드.
  - **쓰기**(PC·패드 등): 오늘만, 잔액 부족이면 이유 표시.
  - 상단에 어제/오늘 전환 + 날짜 선택(운영 시작일~오늘)은 유지하되 "시킨 일"은 날짜 선택의 영향을 받지 않는다.
- **내역**: 최근 거래 내역.
- **설정**: 연결 확인, 마지막 동기화 시각, 연결 해제.

### 7.2 부모용 (탭 4개)
- **현황·승인**: 아들 오늘 상태 요약, **승인 대기 목록**(승인/거절), 탭 아이콘에 대기 건수.
- **정산**: 날짜 선택(어제/오늘/직접), 생활비 적용(항목별 체크·**금액 직접 수정**·식비 0~3끼), 벌금/보너스.
- **관리**: 미션 내주기/삭제, 항목 편집(이름·금액·사용 여부), 월 학원비.
- **설정**: 기기 연결(연결 코드 만들기·기기 목록·해제), 복구 코드, **화면 잠금 PIN**, 초기화(날짜/전체).

### 7.3 처음 실행
- "우리 집 새로 시작하기"(부모) / "연결 코드로 들어가기"(아들·아내).
- 이전 앱 데이터 이어받기는 이번에 **제외** (DB에 가족 데이터가 아직 없음).

## 8. 서버(Supabase) 변경 — 최소·무삭제

모두 `create or replace`(시그니처 동일, `drop` 없음)이라 지난번처럼 승인 팝업에 막히지 않는다. 기존 `supabase.sql`도 같은 내용으로 갱신한다.

1. **`private.build_state`**
   - `missions`: 날짜 필터 제거 → `status <> 'done'` 이거나 최근 3일 안에 만든 완료 건. (`day` 컬럼은 만든 날짜 기록용으로 유지)
   - 새 필드 `recent`: 최근 2일 안에 처리된 요청(승인/거절) — `{id, item_id, mission_id, label, amount, status, decided_at}`. 거절 표시와 "다시 하기"에 사용.
2. **`public.issue_invite`**: 연결 코드를 **8글자**(혼동되는 글자 제외한 31자 알파벳, 약 40비트)로, 유효 **30분**, 1회용. 동시 유효 코드 10개 제한은 유지.
3. **`public.redeem_invite`**: 입력에서 영문/숫자 이외를 제거하고 대문자화한 값의 해시로 조회, 길이는 8자만 허용. (`issue_invite`도 같은 정규화·대문자 값을 해시해 저장. 라이브 DB에 가족 데이터가 없어 기존 24자리 코드 호환은 필요 없다.)
4. 그 외 RPC(`toggle_item`, `request_*`, `decide_request`, `apply_fixed` 등)는 **변경 없음.**
5. 권한: `create or replace`는 기존 권한을 유지한다. 적용 후 `anon`만 실행 가능한지 쿼리로 재확인한다.

## 9. APK 빌드·배포

- 레포 구조: `www/`(앱), `android/`(Capacitor가 생성한 프로젝트, 커밋), `capacitor.config.json`, `package.json`, `.github/workflows/apk.yml`.
- GitHub Actions: Node 22 + Java 17 + Android SDK 설치 → `npm ci` → `npx cap sync android` → `gradlew assembleRelease`(또는 debug) → APK를 **Artifacts**와 **Release**에 올림. `main`에 푸시하거나 수동 실행하면 빌드.
- **서명 키 (결정: 레포 공개 → GitHub Secrets 사용).** 업데이트 설치(덮어쓰기)를 위해 같은 키로 계속 서명해야 한다. 키스토어는 레포에 커밋하지 않는다.
  - 구현 단계에서 키스토어를 한 번 생성해 두고, 사용자가 레포 Settings → Secrets에 4개(`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`)를 직접 한 번 등록한다. 값은 사용자에게만 전달한다.
  - Secrets가 없으면 워크플로는 디버그 서명 APK를 Artifacts로만 올린다(설치는 되지만 덮어쓰기 업데이트는 키가 바뀌어 불가).
  - 공개 레포이므로 Release 파일은 누구나 내려받을 수 있다. 앱에 비밀 값은 없다(Supabase 공개 키와 URL만 포함).
- 설치: 폰에서 GitHub Release의 APK를 받아 설치("출처를 알 수 없는 앱 허용" 필요).

## 10. 오류 처리 요약

서버 오류 코드 → 한글 안내(기존 맵 유지·확장) · 열쇠가 무효(`unauthorized`)면 연결 화면으로 · 네트워크 단절은 띠 + 자동 재시도 · 화면 렌더 중 예외는 전역 핸들러가 토스트로 알리고 앱은 계속 동작.

## 11. 테스트 전략 (이번엔 "실제로 눌러서" 확인)

이 작업 환경은 Supabase와 안드로이드 빌드에 접근할 수 없으므로, 아래로 최대한 실제와 같게 검증한다.

1. **SQL 시나리오**: 로컬 PostgreSQL 16에 `supabase.sql`을 올려 기존 시나리오 + 신규(미션 날짜 무관 노출, 최근 처리 목록, 짧은 연결 코드, 만료/재사용) 단언 테스트. 자정 넘김은 테스트 전용으로 `private.today()`를 바꿔 시뮬레이션.
2. **E2E (핵심)**: 로컬 PG + **PostgREST 호환 얇은 서버**(npm `pg`로 `/rest/v1/rpc/<함수>`를 같은 규약으로 구현; PostgREST 바이너리는 다운로드가 막혀 있음) + Playwright(Chromium) **브라우저 컨텍스트 2개(부모 폰/아들 폰, 390×844)** 로 `www/`를 실제로 띄워 다음을 자동 클릭으로 검증:
   - T1 가족 만들기 → 연결 코드 → 아들 연결
   - T2 **부모가 어제 날짜를 보며 미션 내주기 → 아들 폰에 5초 안에 뜸**(+NEW 배지)
   - T3 자정 넘김 후에도 미완료 미션 유지
   - T4 **아들이 같은 카드 10회 연타 / 서로 다른 카드 빠르게 3개** → 서버 반영 정확, 중복 없음, 동작 유실 없음
   - T5 요청 → 부모 승인 → 아들 "완료" / 거절 → "거절됨" → 다시 요청
   - T6 앱 백그라운드 → 복귀 시 즉시 갱신
   - T7 네트워크 끊김 중 누르기 → "연결 확인 중" → 복구 후 자동 처리
   - T8 생활비 적용(금액 수정, 3끼) → 아들 잔고 반영
   - T9 PIN 잠금(설정/변경/오입력 대기/재잠금)
   - T10 마이너스 차단·파산 규칙
3. **실서버 확인**: 실제 Supabase에 변경 적용 후, 롤백되는 트랜잭션으로 신규 SQL 시나리오를 한 번 더 실행하고 권한(`anon`만 실행) 확인.
4. **CI**: APK 빌드가 성공하고 파일이 올라오는지 Actions 로그로 확인.
5. **이 환경에서 검증할 수 없는 것 (사용자 확인 필요)**: 실제 안드로이드 폰에서의 설치·동작, PostgREST 자체의 세부 동작. 설치 후 확인 체크리스트(§12)를 함께 드린다.

## 12. 열린 질문 · 설치 후 확인 체크리스트

- (해결됨) 레포는 공개 → 서명 키는 GitHub Secrets (§9).
- 설치 후: ① 가족 만들기 ② 연결 코드로 아들 폰 연결 ③ 부모가 미션 내주기 → 아들 폰에 바로 뜨는지 ④ 아들이 요청 → 부모 승인 → 아들 폰 완료 표시 ⑤ 아들이 카드를 빠르게 여러 번 눌러도 모두 반영되는지 ⑥ 앱을 껐다 켜도 로그인 유지 ⑦ 업데이트 APK를 덮어 설치해도 데이터 유지.

## 13. 구현 순서 (계획 단계에서 세분화)

1. 서버 v3 SQL + SQL 시나리오 테스트 → 2. 앱 코어(api/store/ui) + 단위 테스트 → 3. 아들 화면 → 4. 부모 화면 + PIN → 5. E2E 하네스 + 시나리오 T1~T10 → 6. Capacitor 셸 + Actions 빌드 → 7. 실서버 SQL 적용·확인 → 8. 사용자 폰 확인.
